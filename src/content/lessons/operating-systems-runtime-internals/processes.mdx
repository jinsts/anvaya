interviewQuestions:
  - prompt: What is the difference between `fork` and `exec`, and why are they separate calls?
    answer: >-
      `fork` duplicates the calling process: the child gets its own PID and a
      copy of the parent's memory, and `fork` returns the child's PID in the
      parent and 0 in the child. `exec` replaces the program the calling
      process runs while keeping the process and its PID, and it returns
      only when it fails. Keeping them apart lets the child run code between
      them, for example to point its standard output at a file before the
      new program starts, which is how a shell redirects a command's output.
      This describes POSIX systems such as Linux.
    followUps:
      - What runs after `exec` when the program cannot be found?
  - prompt: What is a zombie process, and how do you get rid of zombies?
    answer: >-
      A zombie is a child that has exited but whose parent has not yet waited
      for it. The kernel keeps its PID, exit status and resource usage so
      that the parent can collect them, and it keeps a slot in the process
      table; if the table fills up, no new process can be created. The fix is
      in the parent: it must wait for its children, or set `SIGCHLD` to be
      ignored so they are not kept. If the parent exits, init adopts the
      zombies and waits for them itself.
  - prompt: What happens to a child process when its parent exits first?
    answer: >-
      It becomes an orphan and is reparented, by default to the init process
      of its PID namespace, or to the nearest living ancestor that marked
      itself a child subreaper with `prctl`. `getppid` in the orphan then
      returns the new parent's PID, and the new parent receives its exit and
      waits for it. Nothing else about the orphan changes: it keeps running
      the same program.
  - prompt: Why must the first process in a container reap children, and what goes wrong if it does not?
    answer: >-
      In a container's PID namespace the first process has PID 1 and is that
      namespace's init: every process orphaned inside the namespace is
      reparented to it. If it never waits, each adopted child that exits stays
      a zombie, and they accumulate until process creation fails. A service
      that was not written to reap children should therefore run under a
      small init process as PID 1, or reap them itself. This assumes the
      container has its own PID namespace, as containers normally do.

## A server that starts a worker

`serve` handles one request and exits. A server that takes requests one after
another can start a fresh `serve` for each: a launcher makes a copy of itself,
the copy turns into `serve`, and the launcher waits to hear how it went. On
Linux those are three system calls, `fork`, `exec` and `wait`, made through
the path the [system-calls lesson](/learn/operating-systems-runtime-internals/system-calls/)
traced.

Think of a cell that divides in two, after which one of the copies becomes a
different kind of cell. The analogy stops at copying: a dividing cell
duplicates its contents, but Linux implements `fork` with copy-on-write pages,
so parent and child share the same memory until one of them writes
(fork(2)); the memory chapter shows what that saves.

## fork, exec, exit and wait

<ProcessLifecycle />

**fork** creates a new process by duplicating the calling one. The child gets
its own process ID (PID), and its parent's PID is the caller's. `fork` returns
twice: the child's PID in the parent and 0 in the child, which is how the code
tells the two apart (fork(2)). Which of them runs first is up to the scheduler,
so output from both can come in either order.

**exec** (the `execve` system call and the C library's `exec` functions)
replaces the program the calling process runs. execve(2) calls describing it as
starting a new process "highly misleading": the process and its PID stay; only
the program changes. A successful exec never returns, so nothing after it in
the old program runs. A failed one returns -1, and the code after it does run.

**exit** ends a process; the low byte of its status, 0 to 255, goes to the
parent (\_exit(2)). **wait** collects it. Until then the child is a **zombie**:
it has exited, but the kernel keeps its PID, exit status and resource usage so
the parent can still ask, and it keeps a slot in the process table. If the
table fills up, no new process can be created (wait(2)).

When a parent exits before its children, they are **orphans**. The kernel
reparents each one to init, or to the nearest living ancestor that called
`prctl(PR_SET_CHILD_SUBREAPER)`, and that process waits for it
(wait(2), PR_SET_CHILD_SUBREAPER(2const)).

OSTEP explains why creating a process takes two calls: a shell runs code in
the child between `fork` and `exec`, for example to point the child's standard
output at a file before the command starts.

Read it against the model:

- `serve`'s own line, `serve: ok, 11 bytes`, appears between P1's fork and its
  reap: P2 ran `serve` as P2, with P2's PID.
- P3's exec failed with "No such file or directory", so the code after the
  exec ran and chose status 127.
- P1 waited for P3 with `WNOWAIT`, which leaves a child waitable (wait(2)), so
  P3 was still a zombie: the state field of `/proc/<pid>/stat` was `Z`
  (proc_pid_stat(5)). After P1 reaped it, its `/proc` directory was gone.
- P5 was orphaned when P4 exited, and `getppid` in P5 returned P1's PID: as a
  subreaper, P1 took the place init would have taken, and its `waitpid` for
  P5 worked only because P5 had become its child.

A common mistake is a parent that forks workers and never waits for them. Each
finished worker stays a zombie and holds a process-table slot, however little
else it costs.

## Two-minute recap

- `fork` duplicates the calling process: the child gets a new PID, and `fork`
  returns twice, 0 in the child and the child's PID in the parent.
- `exec` replaces the program a process runs but keeps the process and its
  PID; it returns only when it fails.
- Every child that exits is a zombie, holding its PID and status, until its
  parent waits for it.
- A child whose parent exits first is adopted by init, or by the nearest
  subreaper, which waits for it. In a container, PID 1 inherits that job.
