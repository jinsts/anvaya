interviewQuestions:
  - prompt: What is the difference between a thread and a process?
    answer: >-
      A process has its own address space, descriptor table and process ID. A
      thread is one flow of execution inside a process: it has its own
      registers, stack and thread ID, and shares the process's memory,
      descriptors and process ID with the other threads. On Linux both are
      tasks made by `clone`, whose flags decide what is shared. Threads can
      therefore exchange data through memory directly, which is fast but
      needs synchronization, while processes are isolated and talk through
      the kernel.
  - prompt: One thread writes a global variable. Does another thread see the change? Does a child forked earlier?
    answer: >-
      Another thread can, because it uses the same memory, although it needs
      synchronization to be sure when the write becomes visible. A child does
      not: `fork` gave it a copy of the parent's memory, and writes on either
      side afterwards stay on that side. In this lesson's recording the main
      thread read the 42 its thread wrote, and the 7 the child wrote never
      reached the parent.
  - prompt: Why is calling `fork` in a program that runs several threads risky?
    answer: >-
      The child gets only the thread that called `fork`, but a copy of all the
      memory, including every mutex in whatever state it was. A mutex that
      another thread held is locked in the child, and no thread there will
      ever unlock it, so a child that takes it waits forever. fork(2)
      therefore allows the child only async-signal-safe functions until it
      calls `execve`; the safe pattern is to exec right after forking.

## A second worker in the same process

The [processes lesson](/learn/operating-systems-runtime-internals/processes/)'s
launcher started a new process for each request: a full, isolated copy. A
server can instead start a second **thread** inside the process it already
is. Both run the same program; the question is what they have in common, and
how that differs from a child made by `fork`.

Think of two colleagues in one office. They use the same filing cabinets and
the same phone line, while each has a desk and a notepad. Opening a branch
office as a copy of the first gives the new staff the same files on day one,
but from then on, changes in one office stay there. The analogy stops at the
desks: a thread's stack is its own, but it lies in the same address space as
everything else, so another thread holding a pointer into it can read or
overwrite it.

## What a thread shares, and what a child copies

<AddressSpaces />

POSIX threads in one process "share the same global memory (data and heap
segments), but each thread has its own stack" (pthreads(7)). They also share
the process's open file descriptors and its process ID, while each has its own
thread ID. A child made by `fork` gets the reverse arrangement:
its own process ID, and copies of the memory and the descriptor table that
start identical and then go their own ways (fork(2)).

On Linux both are made by the same system call, `clone`, and its flags decide
what is shared. With `CLONE_VM` the new task runs in the same memory space;
without it, in "a separate copy … as with fork(2)". With `CLONE_FILES` it
shares the descriptor table; without it, it inherits a copy. `CLONE_THREAD`
puts it in the caller's thread group (clone(2)). That is why every thread
reports the same process ID but a unique thread ID: the process ID is the
thread group's (gettid(2)).

pthreads(7) lists more than a dozen other attributes that POSIX makes process-wide and a
few that each thread keeps; the practice asks you to sort them. It also notes
one place where Linux's thread library still departs from POSIX: threads do
not share a common nice value, which matters for scheduling. The figure and the
model describe Linux with glibc's threads, not every system.

## Read threads in /proc

Each thread reads `/proc/thread-self/status`. In a thread's status file,
`Tgid` is the thread group ID, which is the process ID, `Pid` is the thread
ID, and `Threads` is the number of threads in the process
(proc_pid_status(5)). `/proc/<pid>/task/` holds one directory per thread,
named by thread ID (proc_pid_task(5)). In a single-threaded process the
thread ID equals the process ID (gettid(2)).

A common mistake follows from the child having one thread. The child copies
every mutex in the state it was in, and fork(2) warns that a child of a
multithreaded program may call only async-signal-safe functions until it
calls `execve`. Forking and then exec'ing at once, as the launcher did, is the
safe pattern.

## Two-minute recap

- Threads of one process share its memory, descriptor table and process ID;
  each has its own registers, stack and thread ID.
- A forked child gets copies of the memory and descriptors, identical at first
  and independent afterwards, and a process ID of its own.
- On Linux both are made by `clone`; its flags decide what is shared.
- A child forked from a program with several threads has only the calling
  thread, but copies every lock: exec right after forking.
- `/proc/<pid>/status` shows the thread count; `/proc/<pid>/task/` holds one
  directory per thread, named by its thread ID.
