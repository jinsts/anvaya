interviewQuestions:
  - prompt: What is the difference between preemptive and cooperative scheduling?
    answer: >-
      A cooperative scheduler switches only when the running task gives up the
      CPU, by blocking, yielding or finishing, so one task in a loop can keep
      every other waiting. A preemptive scheduler can stop a task that is
      still running, on a timer interrupt or when another task wakes, and run
      another. Linux schedules processes and threads preemptively; some
      runtimes schedule their own tasks cooperatively on top of the kernel's
      threads, which later chapters show.
  - prompt: Two CPU-bound processes share one CPU, one at nice 0 and one at nice 5. What share does each get?
    answer: >-
      Under Linux's weighted fair scheduling the shares follow the weights:
      1024 at nice 0 and 335 at nice 5, so about 75% and 25%. Each step of
      nice changes the weight by about 1.25 times, so the ratio depends only
      on the difference. This assumes both are runnable all the time, on the
      same CPU, in the same scheduling group; in this lesson's recording the
      second process received 24.7% to 24.8%.
    followUps:
      - Why would the same two processes each get a whole CPU on a machine with two idle CPUs?
  - prompt: Why does an I/O-bound task usually get low latency even when CPU-bound tasks are running?
    answer: >-
      A fair scheduler tracks how much CPU each task has had, scaled by its
      weight, and runs the one that has had least. A task that mostly sleeps
      uses little CPU, so when it wakes it is at or near the front instead of
      behind the busy tasks, and it runs within about one slice; Linux can
      also preempt the running task at once when it wakes. Its credit is
      limited, though, so a long sleep does not let it monopolize the CPU
      afterwards.
  - prompt: Why can a CPU-bound background job hurt the tail latency of a service on the same machine?
    answer: >-
      When both want the same CPU, a request that arrives while the job holds
      it may have to wait for the job's slice to end. Most requests are lucky,
      but the unlucky ones wait milliseconds, which shows in the p99 rather
      than the median. In this lesson's recording a sleeping process beside a
      busy one ran within about 0.04 ms at the median, while about one
      wake-up in four waited 2 to 4 ms. Fixes are separating them onto
      different CPUs, raising the job's nice value or putting it in a
      cgroup with a lower weight.

## A web server beside a batch job

A machine runs a web server and a nightly batch job that wants every cycle it
can get. Both are runnable, the CPU can run one at a time, and the kernel's
scheduler chooses. Two questions decide whether the server's users notice: how
much of the CPU each one gets, and how long the server waits when a request
wakes it.

Think of a shared kitchen with one stove and a ledger. Each cook writes down
how long they have used the stove, and whoever has the smallest total cooks
next; a junior cook's minutes are written down at triple weight, so they get
less stove time. The analogy stops at preemption: a cook finishes the step in
hand, but the scheduler takes the CPU away at the end of a slice, or sooner,
whatever the task was doing. OSTEP notes that virtually all modern schedulers
are preemptive.

## Virtual runtime and weights

Linux's default policy for ordinary threads is `SCHED_OTHER`, which the kernel
calls `SCHED_NORMAL` (sched(7)). Its idea, in the kernel documentation's
words, is to model an "ideal, precise multi-tasking CPU" that runs every
runnable task at once, each at an equal fraction of its speed. Real hardware
runs one task at a time, so the scheduler keeps a **virtual runtime** for
each task and runs the one with the lowest: the task that is furthest behind
(CFS Scheduler).

The **nice value**, from -20 to 19, turns into a **weight**: 1024 at nice 0,
3121 at nice -5, 335 at nice 5 (OSTEP chapter 9). A task's virtual runtime
grows by its real runtime × 1024 / weight, so a light task's grows faster and
it is picked less often. sched(7) puts it as a factor of 1.25 for each step of
nice. On Linux the nice value belongs to each thread, not to the process, as
the [threads lesson](/learn/operating-systems-runtime-internals/threads/)
noted. Raising your own nice value needs no privilege; lowering it does
(getpriority(2)).

Linux 6.6 began moving from CFS to **EEVDF**, which keeps virtual runtime and
weights but adds two ideas: a task's **lag**, how much CPU it is owed, makes it
eligible, and among eligible tasks the one with the earliest **virtual
deadline** runs. A waking task can preempt the running one if its deadline is
earlier (EEVDF Scheduler). This lesson's model leaves that out and keeps the
CFS rules OSTEP describes; the recording below shows what the difference does.

## Step through the decisions

The model runs three tasks on one CPU with 3 ms slices: A busy at nice 0, B
busy at nice 5, and C at nice 0, which runs for 1 ms and then sleeps for 3,
like a server handling short requests. It decides when a slice ends or the
running task goes to sleep, and picks the lowest virtual runtime. A task that
wakes takes the larger of its own virtual runtime and the lowest among the
runnable tasks: it cannot bank the time it slept and then hold the CPU to
catch up, but it is not sent to the back either (OSTEP chapter 9).

## What Linux did

`fair.c` pins every process it starts to one CPU with `sched_setaffinity`
(sched_setaffinity(2)), so they compete. It runs two busy processes for 2 s at
nice 0 and 0, then 0 and 5, and reads each one's CPU time from the kernel's
accounting. Then it runs a process that sleeps until every 10 ms mark and
works for 1 ms, and notes how late it woke, alone and beside a busy process.
It sets its timer slack to 1 ns, because by default the kernel may fire a
timer up to 50 µs late to group wake-ups (PR_SET_TIMERSLACK(2const)).

<FairRecording />

The shares match the weights to within a few tenths of a percent. The wake-up
delays are where Linux departs from the model. Beside a busy process, most
wake-ups ran sooner than when the CPU was idle: the waking process preempted
the busy one at once, and an idle CPU probably first had to leave a
power-saving state, which the recording does not show directly. About one
wake-up in four waited 2 to 4 ms, about one slice of the busy process, which
fits EEVDF's rule that a waking task preempts only when its virtual deadline
is earlier; working out which wake-ups wait needs the kernel source, which
this lesson does not go into. The measurement ran on a cloud virtual machine,
not on the owner's WSL2 machine, so other hardware will give other delays.

Every change of who runs is a context switch; the
[context switches lesson](/learn/operating-systems-runtime-internals/context-switches/)
measures what one costs.

A common mistake is to expect a nice value to work across a whole machine.
With autogroups enabled, processes started from different sessions, such as
two terminals, are in different groups, and CPU time is shared between the
groups first; nice then only ranks processes within a group (sched(7)).
`fair.c` starts both processes itself, so they share a group.

## Two-minute recap

- Linux's ordinary threads share a CPU by virtual runtime: the runnable task
  that is furthest behind runs next.
- Nice values become weights, about 1.25 times per step; busy tasks' shares
  follow the weights (24.7% at nice 5 against nice 0, as recorded).
- A task that sleeps uses little CPU, so it runs soon after waking; its
  credit is capped so that it cannot take over the CPU afterwards.
- EEVDF, which Linux adopted from 6.6, also decides when a task wakes: most
  wake-ups preempted the busy process at once, and about one in four waited a
  slice, which shows in tail latency.
