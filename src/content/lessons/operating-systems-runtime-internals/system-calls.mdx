## Two calls that look alike

`serve`, this subject's running example, reads a request from a file and
writes one line of response. On the way it calls `clock_gettime` twice, to
check how long reading took, and `getpid` once, to see whether it is a
container's first process. From C the two look the same: a library function
that takes almost nothing and returns a number. Yet on the machine these
lessons were recorded on, `getpid` took about three times as long. The
difference is where each call's work happens.

Think of a bank. To move money you fill in a slip with a form number and hand
it to a teller, who looks the number up and does the work behind the counter,
where you cannot go. To learn the time, you read the clock in the lobby. The
analogy stops at the clock: the lobby clock gives everyone the same answer,
and that is exactly the limit of the kernel's shortcut. It serves only answers
the kernel can publish to every process, such as the time; anything that needs
the kernel to act for you, such as reading a file, still goes to the counter.

The [hardware–software lesson](/learn/computer-architecture-execution/hardware-software-interaction/)
showed how the CPU enters the kernel with a privilege change and returns to a
saved resume point. This lesson follows what the kernel does with a request
once it is in, and the shortcut that skips the trip.

## From a library call to the kernel and back

<SyscallPath />

A **system call** is a request to the kernel, made by number. On x86-64 Linux,
the C library's wrapper for `getpid` puts the number 39 in the eax register and
any arguments in rdi, rsi, rdx, r10, r8 and r9, then runs the `syscall`
instruction; syscall(2) lists these registers for every architecture. The
instruction enters the kernel at the entry point for 64-bit system calls. The
entry code saves your registers, checks that the number is valid and runs the
handler that the **system-call table** holds at that index. The kernel's
source lists the table one line per number, in
`arch/x86/entry/syscalls/syscall_64.tbl`.

Asking by number is a protection, as OSTEP puts it: your code cannot name a
kernel address to jump to, only a service to request. The handler's result
comes back in rax. A negative result is an error number, which the wrapper
turns into a return value of -1 and the error in `errno` (intro(2)). `read`
takes the same path with number 0; its handler copies bytes from the file into
your buffer.

The **vDSO**, the virtual dynamic shared object, is the shortcut. The kernel
maps this small shared library into every process and keeps data in memory the
process can read, so that a frequent call whose answer is no secret becomes an
ordinary function call and a few memory accesses. The C library calls it for
you. vdso(7) lists four such functions on x86-64: `clock_gettime`,
`gettimeofday`, `time` and `getcpu`. `getpid` is not among them, and since
glibc 2.25 the C library no longer caches the process ID, so every `getpid`
is a system call (getpid(2)).

The figure is a model of the order of steps on x86-64 Linux with glibc, not of
the kernel's code: the real entry path does more on the way in and out than
these three kernel boxes, and other architectures use other instructions and
registers.

Read it line by line:

- `openat(…) = 3`: since glibc 2.26 the C library's `open` makes the `openat`
  system call, and the new descriptor is the lowest number not already open
  (open(2)). Descriptors 0, 1 and 2 are standard input, output and error
  (stdin(3)).
- `read(3, "GET /hello\n", 255) = 11`, then `read(3, "", 244) = 0`: a read
  returns the bytes it got, and 0 means end of file (read(2)). Reading a whole
  file always takes one read more than its size requires, the one that finds
  nothing.
- `close(3) = 0` and `getpid() = P1`: two more requests; serve is not PID 1,
  so it answers normally.
- `write(1, …, 20) = 20`: the whole response in one call to standard output.
- `exit_group(0) = ?`: it ends every thread in the process and does not
  return (exit_group(2)), so its result is `?` and strace prints the exit on
  the next line.

A common mistake is to count system calls by reading source code. The source
shows library calls: some, like `clock_gettime`, make no system call, and a
program makes many calls of its own before `main` runs. Count with the tool.

## Two-minute recap

- A system call is a request to the kernel by number. On x86-64 Linux the
  number goes in eax and the arguments in rdi, rsi, rdx, r10, r8 and r9; the
  result comes back in rax, and the C library turns a negative result into -1
  and `errno`.
- The kernel's entry code saves your registers, checks the number and runs the
  handler that the system-call table holds for it.
- The vDSO answers a few frequent, non-secret calls such as `clock_gettime`
  inside your process, with no system call, so strace never sees them.
- A small program makes more system calls than its source shows: serve's run
  counted 35, and 29 of them started the program. `exit_group` never returns,
  so strace -c does not count it.
- strace stops a program twice for each system call: `getpid` became hundreds
  of times slower under it, while `clock_gettime` did not change.
