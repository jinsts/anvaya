  - prompt: What happens in a context switch, and what does it cost?
    answer: >-
      The kernel saves the running task's registers, program counter and
      kernel stack pointer and restores those of the next task, which then
      returns to user space where it left off. The direct cost is about a
      microsecond on current hardware; in this lesson's recording on a cloud
      virtual machine it was about 1.2 µs between processes and 1.0 µs
      between threads at the median. The indirect cost can be larger: the next
      task finds caches and the TLB filled with someone else's data and
      translations, and pays in misses afterwards.
  - prompt: What is the difference between a voluntary and an involuntary context switch?
    answer: >-
      A voluntary switch happens when the task gives up the CPU itself, by
      blocking on I/O, a lock or a sleep. An involuntary one happens when the
      kernel takes the CPU away from a task that could still run, because its
      slice ended or another task woke with a better claim. Linux counts both
      per thread in `/proc/<pid>/status`. Many involuntary switches suggest
      CPU contention; many voluntary ones suggest a task that waits a lot.
    followUps:
      - A service shows involuntary switches climbing while its latency rises. What do you check next?
  - prompt: Why does a thread-per-request server stop scaling?
    answer: >-
      Each request costs a thread's stack and kernel structures, and while
      the threads outnumber the CPUs, each switch between them costs about a
      microsecond plus the cache and TLB misses afterwards. With thousands of
      mostly blocked threads the switches and the memory add up, and under
      load the scheduler spreads CPU across all of them, so tail latency
      grows. Event loops and runtimes with their own lightweight tasks
      multiplex many requests over few threads instead; the runtime chapters
      cover them.
  - prompt: Why is switching between two threads of one process cheaper than between two processes?
    answer: >-
      Threads of one process share an address space, so the kernel does not
      switch page tables, and on hardware without address-space tags the TLB
      keeps its translations. Between processes it must switch page tables,
      and the TLB either is flushed or relies on address-space identifiers.
      The register save and restore is the same. In this lesson's recording
      the difference was about 0.2 µs at the median; the indirect cost on a
      real workload can differ more.

## What the scheduler's decisions cost

The [scheduling lesson](/learn/operating-systems-runtime-internals/scheduling/)
counted who runs; every change of who runs is a **context switch**, and it is
not free. A server with one thread per request switches each time a request
blocks and another becomes ready. How much does one switch cost, and when does
it matter?

Think of a desk shared by two people in shifts. At a change of shift, the
first packs their papers into a drawer and the second unpacks theirs. The
analogy stops at what is left behind: the next person does not only unpack,
they also find the shelves within reach full of the other person's books.
Caches and the TLB play the shelves, and the cost of refilling them comes
after the switch, not during it.

## What a switch saves and restores

When the kernel has the CPU, after a system call or a timer interrupt, the
scheduler may choose another task. The switch itself saves the running task's
general-purpose registers, program counter and kernel stack pointer, and
restores those of the next task; returning from the kernel then resumes the
next task where it stopped (OSTEP chapter 6). The
[hardware lesson](/learn/computer-architecture-execution/hardware-software-interaction/)
showed how the CPU enters and leaves the kernel.

The indirect costs come later. Between processes the page tables change too,
and the TLB's translations belong to the old process, so it is flushed or its
entries are told apart by an address-space identifier (OSTEP chapter 19).
Threads of one process share the address space, so a switch between them
keeps the page table (OSTEP chapter 26). Either way, the next task's data is
probably no longer in the caches the
[memory hierarchy lesson](/learn/computer-architecture-execution/memory-hierarchy-and-caches/)
described.

Linux counts switches for each thread in `/proc/<pid>/status`:
`voluntary_ctxt_switches` when it gave up the CPU, for example by blocking,
and `nonvoluntary_ctxt_switches` when the kernel took the CPU away while it
could still run (proc_pid_status(5)).

## Measure a switch with a ping-pong

A switch is too short to time alone, so OSTEP describes how lmbench measures
it: two tasks on one CPU pass a byte back and forth through two pipes. Each
blocks in `read` until the other writes, so every round trip makes two
switches. Pinning both to one CPU with `sched_setaffinity`
(sched_setaffinity(2)) makes the switch happen on one CPU instead of the two
tasks running side by side on two.

<RoundTrip />

A round trip also does two writes and two reads, so `switch.c` times the same
pipe work done by one process alone, with no switch, and the model subtracts
it: one switch costs (ping-pong − pipe) / 2. It times 15 batches of 100,000
round trips for a parent and a forked child, for two threads, and for the pipe
work alone, rotating the order every batch so that a slow stretch of the
machine does not land on one kind.

Predict before you look: is a switch between two threads cheaper than one
between two processes, and by how much?

The counts in the figure answer a second question. Every round trip took the
measuring thread off the CPU exactly once, but /proc counted a little over
half of those switches as voluntary and the rest as involuntary. The likely
reason is the scheduling lesson's wake-up preemption: when the thread writes,
its partner wakes and often takes the CPU before the thread reaches its own
`read`, so the thread is preempted while it could still run.

The tests check that a round trip has two switches, that the estimate agrees
with a hand computation on the first three recorded batches, that each
ping-pong batch is paired with its own batch's pipe timing, and that every
recorded round trip switched the measuring thread out once. The median and
p90 follow the
[measuring-performance lesson](/learn/computer-architecture-execution/measuring-performance/)'s
convention and reuse its code.

A common mistake is to measure without pinning. On an idle machine with
several CPUs the two tasks can each run on a CPU of their own, and the
ping-pong then measures waking a task on another CPU, not switching on one.

## Two-minute recap

- A context switch saves one task's registers, program counter and kernel
  stack pointer and restores another's; between processes the page tables
  change too.
- Its indirect cost is the cache and TLB misses the next task pays
  afterwards.
- `/proc/<pid>/status` counts voluntary switches (the task blocked) and
  involuntary ones (the kernel took the CPU away).
- Pinned to one CPU of a cloud VM, one switch cost about 1.2 µs between
  processes and 1.0 µs between threads at the median: small alone, but large
  when thousands of threads take turns.
