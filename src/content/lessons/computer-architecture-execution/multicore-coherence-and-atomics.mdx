interviewQuestions:
  - prompt: What does cache coherence guarantee, and what does it not?
    answer: >-
      Coherence keeps the cached copies of each memory location consistent:
      once a write to a location is visible, no core keeps reading an older
      value of that location from its own cache. Protocols such as MESI do this
      per cache line, by giving one cache ownership before it writes and
      invalidating the other copies. Coherence says nothing about the order in
      which other cores see writes to different locations, and it does not make
      a load, an add and a store into one indivisible update. Those need memory
      ordering and atomic operations.
  - prompt: What is false sharing, and how do you fix it?
    answer: >-
      Coherence works on whole cache lines, so two threads that write
      different variables in the same line keep taking ownership of the line
      from each other, although they share no data. Every write becomes a
      coherence miss and the program slows down. Fix it by putting data written
      by different threads on different lines, with alignment or padding, or by
      having each thread accumulate locally and merge once at the end. Measure
      before and after; the line size and the effect depend on the machine.
  - prompt: Why is publishing data with an ordinary flag unsafe, and how do release and acquire fix it?
    answer: >-
      The compiler and the processor may reorder accesses to different
      locations, so a reader can see the flag set and still read the old data.
      In C or C++ an unsynchronized flag is also a data race. Storing the flag
      with release ordering keeps every earlier access before it; loading it
      with acquire ordering keeps every later access after it. A reader whose
      acquire load sees the release store is then guaranteed to see the data.
    followUps:
      - Does a release store followed by an acquire load in the same thread act as a full fence?
  - prompt: If the CPU caches are coherent, why can two increments still lose an update?
    answer: >-
      An ordinary increment is three steps: load, add and store. Coherence
      makes each step see a consistent copy of the line, but both threads can
      load 7 before either stores, and then both store 8. An atomic
      read-modify-write, such as a fetch-and-add, holds the line for the whole
      update, so no other write can come between its load and its store. A lock
      also works. Flushing caches would not help.

## Several cores, one memory

Each core has at least its own L1 cache, so two cores can hold copies of the
same cache line. Three separate questions follow, and mixing them up causes most
multicore bugs:

- **Coherence:** do the copies of one location agree?
- **Ordering:** in what order can other cores see writes to _different_
  locations?
- **Atomicity:** can a multi-step update, such as load, add, store, happen
  without another core's write in the middle?

Hardware answers the first for you. The second and third you request with
atomic operations, and with the locks and other primitives built on them.

## Coherence: one owner before a write

A coherence protocol tracks every cached line's state. In **MESI**, a line in a
cache is Modified (the only copy, changed), Exclusive (the only copy, clean),
Shared (clean, other caches may hold it too) or Invalid. A read that misses
announces itself, and any other copy drops to Shared. A write needs the only
valid copy, so a cache holding the line Shared or not at all sends a **request
for ownership** that invalidates every other copy. A line held Exclusive becomes
Modified silently, since there is no one to tell.

Think of a document that many people may read but only one may edit, after
collecting everyone else's copy. The analogy stops at granularity: a cache does this
for every 64-byte line separately, whatever the line holds.

## False sharing: the line is the unit

Coherence does not know about variables, only lines. Two threads that write
different counters in one 64-byte line take the line from each other on every
write, though they share no data. This is **false sharing**. Padding the
counters onto separate lines leaves each line with one writer, and after the
first write each core keeps its line Modified:

<FalseSharing />

The measurement ran `false_sharing.c`: two threads, each adding 1 to its own
`volatile` counter, with the counters either 8 bytes or 64 bytes apart. The
`volatile` only stops the compiler from keeping the counter in a register; the
threads never touch each other's counter, so there is no data race. Sharing a
line made each increment several times slower on this machine. The threads
were not pinned to particular cores, and the ratio depends on the processor.

Fix false sharing by keeping data written by different threads on different
lines: align or pad per-thread data, or have each thread accumulate in a local
variable and write the shared result once. Padding costs memory, so measure
before applying it everywhere.

## Ordering: publishing data with a flag

A common pattern publishes data through a flag: the writer stores the data,
then sets the flag; the reader waits for the flag, then reads the data. With
ordinary accesses nothing guarantees that the reader sees the data once it sees
the flag. The compiler may reorder accesses to different locations, and so may
the processor, which keeps executing while earlier stores and loads are still
in flight. In C and C++ a plain flag shared between threads is also a data race,
which is undefined behavior.

**Release** and **acquire** orderings fix the pattern. The Linux kernel's
memory-barrier documentation calls them one-way barriers: no access before a
release store may appear after it, and no access after an acquire load may
appear before it. When the reader's acquire load sees the writer's release
store, everything the writer did before the release is visible after the
acquire.

<LitmusOutcomes />

Without ordering, the model allows all four outcomes, including the dangerous
one: the flag set but the old data. With release and acquire, that outcome is
gone. The model only reorders each thread's accesses within the rules above and
then interleaves the two threads; it is a teaching model, not the C memory
model, and whether a particular processor ever produces the stale outcome varies
by architecture.

On x86-64 the release store and the acquire load are ordinary `movl`
instructions: there the ordering costs no extra instruction, but it still stops
the compiler from moving the data store after the flag store or the data load
before the flag load. On AArch64 they become `stlr`, a store-release, and
`ldar`, a load-acquire, while the data accesses stay plain `str` and `ldr`.

defines it as a total order with all other sequentially consistent operations,

## Atomicity: one indivisible update

Two threads incrementing one counter shows that coherence and atomicity are
different. An ordinary `counter++` is a load, an add and a store, and the other
thread can run between them:

<LostUpdate />

Coherence was working the whole time: every load read the current value of the
line. What went wrong is that B's load came between A's load and A's store. An
**atomic read-modify-write** removes that gap. On x86-64 a relaxed
`__atomic_fetch_add` compiles to one instruction with a `lock` prefix, which
makes the load, the add and the store one indivisible operation:

<CodeExample title="count_hit, x86-64 -O2" code={countHit} language="text" />

A racing plain `counter++` in C is undefined behavior, so the figure is a model
of the steps, not a prediction of what a compiler would emit. The native lab
does run the atomic version for real: two threads each call `count_hit` a
million times, and the total is exactly 2,000,000 at `-O0` and `-O2`. In
JavaScript, `Atomics` provides atomic operations, including add, on shared
typed arrays.

Relaxed ordering is enough for a counter that is only read after the threads
finish. If the counter also publishes other data, use release and acquire as
above.

## Costs beyond one line

- **Hardware threads** on one core share its execution units and caches, so two
  busy threads on one core do not run twice as fast; Drepper's paper discusses
  when they help.
- **NUMA** machines attach memory to each processor socket, and reaching another
  socket's memory takes longer.
- Locks, condition variables and deadlock are built on these atomic operations;
  the operating-systems subject covers them.

Neither cost was measured here.

thread can load before its own store is visible, and both read 0. The kernel
documentation says the same: a release followed by an acquire is not a full

## Two-minute recap

- Coherence, ordering and atomicity are three different guarantees; hardware
  provides only coherence by default.
- MESI gives one cache ownership before a write and invalidates the other
  copies; writing a line another core holds costs a request for ownership.
- Coherence works per line, so threads writing neighboring variables slow each
  other down: false sharing. Separate their data onto different lines.
- Publish data with a release store and read it with an acquire load; release
  and acquire are not a full fence.
- Coherent caches still lose plain increments; use an atomic read-modify-write
  or a lock.
