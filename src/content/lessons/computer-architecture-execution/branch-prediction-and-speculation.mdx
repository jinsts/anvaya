## Waiting for branches would waste the pipeline

The [pipelining lesson](/learn/computer-architecture-execution/pipelining-and-hazards/)
flushed two instructions for every taken branch, because the branch resolved in
EX. Real processors fetch several instructions per cycle and resolve branches
many stages after fetch, so waiting for every branch, or flushing after it,
would waste most of the machine. Instead they **predict** each branch's outcome,
keep fetching down the predicted path, and **speculatively** execute it.

A good predictor is like a commuter who takes the usual road without checking
traffic each morning: right almost every day, and the occasional wrong guess
costs a detour. The analogy stops at the cost: a misprediction discards every
instruction fetched down the wrong path, which in a deep pipeline is a lot of
work.

## A two-bit counter learns a branch's habit

The simplest dynamic predictor remembers each branch's last outcome. A **two-bit
saturating counter** adds hysteresis: it steps toward each outcome and stops at
its ends, so one surprise only weakens a strong prediction.

<PredictorStates />

For a loop branch that is taken five times and then exits, the counter
mispredicts once per exit; repeating the last outcome mispredicts twice, at the
exit and again on re-entry. An alternating pattern defeats both: real processors
add predictors that use the history of recent outcomes.

Before stepping, look at the predictor's state and the pattern so far, and say
whether the next guess will be right.

## Measure what a misprediction costs

The same bytes, summed with the condition `value >= 128`, give a branch that
random data makes unpredictable and sorted data makes almost perfectly
predictable. The native lab compiled one C function three ways and timed it on
both orders:

<SortedRandom />

Only the third build depends on the order. Its listing still contains the
condition as a jump, `jns`, which the predictor must guess for every element.
GCC removed the branch from the other two: at `-O1` it computes both outcomes and
selects one with a conditional move, `cmovs`, and at `-O2` it vectorizes the loop,
comparing sixteen bytes at a time into a mask. With no branch to mispredict,
the order no longer matters. The `-O1` build is slower than the sorted branch
build because it always does the extra work; the vector build is fastest.

The lesson for any "sorted is faster" benchmark: **read the generated code
before explaining the timing.** The effect you are measuring may not exist in the
binary.

## Run ahead, commit in order

Prediction keeps the front of the pipeline busy. **Out-of-order execution** keeps
the back busy: instead of stalling behind an instruction that waits, such as a
load that misses the cache, the core executes later instructions whose operands
are ready.

<ReorderBuffer />

Instructions enter a **reorder buffer** in program order and may execute out of
order, but each result becomes architectural, visible in registers or memory,
only when the instruction **commits**, and commits happen in program order. If a
branch was mispredicted or an older instruction faults, every younger
instruction is discarded before it commits. The program therefore sees the
same results as sequential execution, with exceptions reported at the right
instruction.

## Speculation leaves traces

Discarding speculative work restores registers and memory, but not everything:
a speculative load can still bring a line into the cache. **Spectre** showed that
an attacker can mistrain a predictor so that code speculatively reads data it
should not, encodes it in which cache line it touches, and then recovers it by
timing reads.

<SpectreSteps />

The defenses work on different steps: speculation barriers such as `lfence` on
sensitive branches stop the speculative read, masking an index so an
out-of-bounds value cannot be formed removes what it reads, and keeping secrets
out of the address space of untrusted code removes the target. Each costs some
performance, which is why they are applied selectively.

## Two-minute recap

- Processors predict branches and speculatively execute the predicted path;
  a misprediction discards the wrong-path work.
- A two-bit counter mispredicts a loop branch once per exit; alternating and
  random outcomes defeat simple counters.
- A data-dependent branch made random data several times slower than sorted
  data, but only in the build that kept the branch.
- Out-of-order cores execute ready instructions early and commit results in
  program order through a reorder buffer.
- Speculation leaves cache traces that Spectre turns into a leak; defenses stop
  speculative reads on sensitive paths.
