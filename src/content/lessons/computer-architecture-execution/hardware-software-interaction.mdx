## A function call cannot grant permission

Suppose an image editor saves a photograph. Its arithmetic instructions execute
directly on the CPU, but it cannot overwrite an arbitrary storage device block.
Other processes and the operating system share that hardware. The system needs a
controlled way to request a write while preserving isolation.

Think of an office service desk: anyone may submit a request, while only staff
can operate the locked equipment. The analogy stops at enforcement. A CPU's
privilege checks are hardware rules, not a convention that cooperative programs
may ignore.

**User mode** restricts operations available to applications. **Kernel mode**
permits the operating system to manage protected resources. Exact privilege
levels and instruction names depend on the architecture. A normal function call
changes control flow within the current privilege context; it does not make the
callee privileged.

An **application binary interface**, or ABI, defines binary agreements such as
argument registers, return values, stack alignment, and executable conventions.
A syscall ABI additionally defines how a request number and arguments reach the
kernel. Knowing a calling convention does not itself authorize a request.

An **exception** is an event associated with executing an instruction. An
**interrupt** arrives from a source such as a timer or device rather than being
caused by the program's current instruction. Terminology varies by ISA; here,
“synchronous” means tied to the instruction stream.

The boundary figure distinguishes deliberate requests, synchronous faults and
asynchronous notification. The trigger determines which operation can resume.

A page fault does not always mean a program bug or a storage read. The operating
system might provide a newly allocated page, establish a mapping, or terminate
an invalid access. The faulting operation can be retried only when the handler
has made that safe and the architecture supports the required restart behavior.

For a syscall, the wrapper supplies the request and arguments; protected entry
establishes a safe context, the kernel validates and services the request, and
return code restores the authorized continuation.

Hardware and entry code divide the saving work differently across systems.
Entering the kernel also does not necessarily switch processes: the same thread
may run kernel code and return directly. A blocking request can instead let the
scheduler run another thread.

The lab models a CPU using **instruction indices**, not byte addresses. A syscall
at index 12 consumes that instruction and saves 13. A restartable fault at 12
saves 12. An interrupt arrives between instructions, so its current index already
names the next instruction to execute.

## Addresses and device registers have different contracts

An application's pointer usually names a **virtual address**. The processor's
memory-management unit translates authorized accesses to physical memory using
configuration managed by the operating system. Two processes can use the same
virtual number for different physical pages. A valid pointer in one process is
therefore not a universal address.

**Memory-mapped I/O**, or MMIO, exposes device control or status registers in an
address range. Reading such a register can acknowledge an event; writing it can
start work. It follows the device's access widths, ordering, and mapping rules.
Treating it as an ordinary cached array can be incorrect.

A **driver** translates an operating-system request into a device protocol. It
may set up buffers, write registers, submit a queue entry, and process completion.
Device-accessible memory may need a separate mapping, possibly through an IOMMU,
which translates device requests and can restrict their access. An application's
pointer does not establish that mapping or keep a buffer alive.

The next lesson follows [I/O submission and completion](/learn/computer-architecture-execution/io-mechanisms/).
The boundary matters even when an API hides every register: a call that returned
success may only have copied data into an operating-system buffer.

## Coherent does not mean synchronized

**Cache coherence** coordinates cached copies of the same memory location.
Protocols such as MESI describe states including modified, exclusive, shared,
and invalid. Coherence does not turn a sequence of instructions into one atomic
operation, nor does it by itself establish the ordering of a protocol spanning
several locations.

For example, imagine two threads both load counter value 7, each computes 8, and
each stores 8. A coherent memory system can carry out that sequence faithfully:
one increment is still lost. This is a reasoning trace, not runnable concurrent
code. The language's concurrency rules determine whether ordinary concurrent
accesses are allowed; the trace is not a promise that arbitrary racy source
code will compile to these steps.

**Memory consistency** specifies which observations of reads and writes are
allowed. Store buffers and other optimizations can make cross-location ordering
less intuitive than source order suggests. Use the language's locks and atomic
operations to express synchronization; their implementation supplies the
necessary compiler and hardware constraints.

For JavaScript shared-memory programming, use the specified `Atomics` operations
on supported shared typed-array views when atomic operations are required.
This lesson's lab uses no shared memory and tests no concurrency protocol.

## Trace visibility separately from atomicity

Imagine core A holding a cache line containing x in a modified state. Core B
requests that line: coherence must obtain the current data and appropriate
permissions rather than read a stale backing-RAM copy. In a MESI-style model,
shared read copies differ from exclusive write ownership. The exact transition
protocol is processor-specific.

Now A writes payload at one location and a ready flag at another. A store buffer
can defer visibility while A continues executing. Coherence of each location
alone does not establish the cross-location publication order. A correct protocol
uses the language's release/acquire operations or locks. Acquiring the published
flag must pair with publication of the payload; ordinary loads/stores are not a
substitute. This is a conceptual protocol, not tested concurrent C code.

**Diagnosis:** a trace says both cores read counter 7 and later store 8. Is the
first error necessarily stale caching? No: even a coherent order can lose an
update when load/add/store is not an atomic read-modify-write. Identify which
property is needed before proposing a cache flush.

## Two-minute recap

- Ordinary calls preserve privilege; system calls enter through controlled mechanisms.
- Syscalls, synchronous exceptions, and interrupts differ in cause and resumption rules.
- A kernel entry need not change which process is running.
- Virtual pointers, device addresses, and MMIO registers have distinct contracts.
- Coherence does not make a multi-instruction update atomic or establish every ordering.
- Drivers and synchronization primitives make hardware requirements explicit for software.
