  - prompt: Are DMA and interrupts competing ways to perform I/O?
    answer: >-
      They answer different questions. DMA moves data between a device and memory
      without having the CPU copy each transferred word. An interrupt tells the
      CPU about an event such as completion, while polling discovers status by
      checking it. A DMA device can use either notification strategy, and drivers
      can combine them according to load.
  - prompt: Why can polling sometimes be useful even though it consumes CPU time?
    answer: >-
      A waiting CPU can check a completion queue without paying an interrupt and
      scheduling transition for every event. That may suit a busy queue or a
      strict latency target when dedicating CPU capacity is acceptable. For sparse
      or slow events, repeated checks can waste substantial CPU time and energy.
      Compare the arrival pattern, batching policy, and opportunity cost before
      choosing a strategy.
  - prompt: What does interrupt coalescing trade?
    answer: >-
      The device waits before raising an interrupt, so completions that arrive
      meanwhile are delivered together and the CPU enters its handler fewer
      times. The price is latency: the first completion of a batch waits for the
      others or for a timeout. A batch limit and a timeout bound that wait, and
      both are tuned to the arrival rate. Under heavy load it also helps avoid
      spending all the CPU's time entering handlers.
    followUps:
      - How would you pick the timeout for a latency-sensitive service?
  - prompt: How does Linux's NAPI combine interrupts and polling?

      In basic operation the device raises an interrupt, and the driver schedules
      a NAPI instance and keeps the device's interrupts masked while it polls.
      Each poll processes at most a budget of packets, and while work remains the
      instance is polled again without new interrupts. When the queue drains the
      driver completes NAPI and unmasks interrupts. So a busy device is polled,
      and an idle one wakes the CPU only when something arrives.

## Two questions about every transfer

A disk driver sends a 4 KiB block and then spins, reading a status register
until the disk says it is done, while another process waits for the CPU. Two
separate costs are mixed up in that loop: the CPU copying the data, and the CPU
checking whether the device has finished. Each has its own fix.

Think of waiting for a kettle: you can stand and watch it, or go and do
something else until it whistles. The analogy stops at batching: a kettle
whistles once for one kettle, while a device can hold back its signal so that
one interrupt reports several finished requests, and one check of a queue can
find many.

The [hardware boundary lesson](/learn/computer-architecture-execution/hardware-software-interaction/)
showed how an interrupt enters the kernel. This page asks who moves an I/O
request's bytes and how software learns that the device finished; the
[I/O mechanisms lesson](/learn/computer-architecture-execution/io-mechanisms/)
then follows one request's buffer from submission to reuse.

## Who moves the bytes

In **programmed I/O** (PIO), the CPU performs the accesses that transfer the
payload through a device interface, one word at a time. In **direct memory
access** (DMA), a device or DMA engine transfers the payload between the device
and memory. The CPU still sets up the operation, telling the engine where the
data is, how much to move and which device takes it, and handles completion
and errors.

<TransferTimeline />

OSTEP's devices chapter draws the same contrast: with PIO the CPU is busy for
the whole copy, while with DMA it can run another process until the engine
raises an interrupt to say the transfer is done. DMA has costs of its own:
setup, memory the device may access, and rules about who owns a buffer while it
is in flight, which the I/O mechanisms lesson covers.

## How software notices

**Polling** reads device status or a completion queue repeatedly. An
**interrupt** signals an event so the CPU can enter a handler. Polling and
interrupts do not determine whether the payload was moved with PIO or DMA.

| Programmed I/O | CPU participates in payload transfer   | Simple for small interfaces; consumes CPU work per transfer               |
| DMA            | Device or engine transfers the payload | Requires setup, valid memory mappings, and ownership discipline           |
| Polling        | Software checks status                 | Can reduce notification overhead at high load; spends CPU time checking   |
| Interrupts     | Hardware announces events              | Avoids constant checks for sparse events; handling and wakeups have costs |

Polling every 4 units finds the completion at 12, two units late, after two

interrupt costs no checks but enters a handler for every event it announces.

Interrupts are not always better. OSTEP notes that for a fast device the first
poll usually finds the work done, so switching away and taking an interrupt
only adds cost; that a flood of interrupts can leave a system handling nothing
else; and that a hybrid can poll briefly before waiting for an interrupt.

## Batching changes the count

When completions arrive close together, one poll can find several, and a
device can **coalesce** interrupts: wait a little before raising one, so that
completions arriving meanwhile share it. Waiting saves handler entries and adds
latency.

that raises one interrupt when three completions are waiting or four units
after the oldest. Which costs the most handler entries, and which delays some
completion the longest?

An interrupt per completion costs five handler entries and no delay. Coalescing
costs two entries: the first fires at 11, when three are waiting, and the second
at 16, the timeout after the completion at 12, which waits 4 units, the longest
delay here. Polling every 4 finds four completions with one check at 12 and the
last at 16, after two empty checks. Which is best depends on what a delay costs
the program and what an entry costs the CPU.

</details>

Linux's network stack combines the two. In basic operation the device raises an
interrupt, and the driver keeps that device's interrupts masked while a NAPI
instance polls it, processing at most a budget of packets per poll and polling
again while work remains; only when the queue drains are interrupts unmasked.
**Busy polling** goes further and checks for packets before any interrupt,
trading CPU cycles for lower latency, as the kernel's NAPI documentation puts
it.

Three measures can move in different directions. **Latency** is the time until
a particular request reaches the specified finish line. **Throughput** is
completed work per unit of time. **CPU cost** is processor effort spent on
submission, transfer, checking and handling. Batching can raise throughput by
spreading notification overhead across requests while a request waiting for
the batch sees higher latency.

## Two-minute recap

- Programmed I/O and DMA decide who moves the payload; polling and interrupts
  decide how software learns of progress.
- DMA frees the CPU during the copy, at the cost of setup and buffer-ownership
  rules.
- Polling spends checks, and an interrupt spends a handler entry per
  announcement; which costs more depends on the arrival pattern.
- Coalescing and batched polls trade latency for fewer notifications.
- Compare latency, throughput and CPU cost at a stated finish line.
