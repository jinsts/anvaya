interviewQuestions:
  - prompt: How would you benchmark a change to show that it is faster?
    answer: >-
      State what should get faster and why. Fix the input, sizes, compiler
      flags and machine, and decide what is inside the timed region, including
      whether caches start warm or cold. Check that both versions produce the
      same result. Run each many times, interleaving the two so drift affects
      both, and compare distributions, such as medians and percentile ranges,
      rather than single runs. Then test the proposed cause separately, with
      the generated code or hardware counters.
  - prompt: Why report a median and percentiles instead of the mean of the runs?
    answer: >-
      Timing noise is lopsided: interrupts, other processes and frequency
      changes only ever add time, so a few slow runs pull the mean up. The
      median describes a typical run and is not moved by a handful of
      outliers, while percentiles such as p10 and p90 show the spread. If two
      candidates' ranges overlap heavily, more runs are needed before claiming
      a difference.
  - prompt: What does a roofline model tell you about a kernel?
    answer: >-
      Attainable performance is the lower of the machine's peak compute rate
      and its memory bandwidth times the kernel's operational intensity, the
      operations it performs per byte moved from memory. A kernel left of the
      ridge point is bounded by bandwidth, so faster arithmetic such as SIMD
      cannot help until it moves fewer bytes; a kernel right of it is bounded
      by compute. The roofline is an upper bound, not a prediction.
  - prompt: What do hardware counters add to a timing, and what can mislead you?
    answer: >-
      Counters such as cycles, instructions, branch misses and cache misses
      test why a run took its time: a lower IPC or a higher miss count can
      support or refute a hypothesis. Pitfalls: event names map to
      model-specific events, so check their definitions; when more events are
      requested than the hardware can count at once, the tool multiplexes and
      scales the counts; hybrid processors count each core type separately;
      and the counts cover everything in the measured command, not just the
      loop you care about.

## One run is not a measurement

Time a sprinter once and you learn about that race: the wind, the start, the
runner's morning. Time them thirty times and you learn about the runner. A
program is the same. Caches, the operating system, other processes and the
clock frequency all change from run to run, so one timing mixes the program
with its circumstances. The analogy stops at control: unlike a race, you can
fix most of the circumstances, and you should.

rather than running all of A and then all of B, spreads slow drifts such as
heating or a background job across both.

Three things show up even in this simple, checked experiment:

- **Each series spreads widely.** The same code on the same data took more
  than one and a half times as long in its slowest run as in its fastest. One
  run of each would have told you almost nothing.
- **The medians differ but the ranges overlap.** Evicting the array made the
  typical run slower, but many cold runs were faster than many warm ones. The
  pairing figure in the caption says how often a single pair of runs would have
  ranked them the wrong way.
- **Cache state is part of the workload.** The array is smaller than this
  machine's L3 cache, and a sequential scan is easy for the hardware to
  prefetch, so the gap is modest; a random access pattern or a larger array
  would behave differently. Say which state your benchmark measures.

The runs were not pinned to a core, ran under WSL2, and recorded no clock
frequency, so the spread includes all of that. Report such limits with the
numbers.

## Bound a kernel with a roofline

A timing says how fast a kernel ran, not how fast it could run. The **roofline**
model gives the bound. A kernel's **operational intensity** is the number of
operations it does per byte it moves to or from memory. A machine can supply at
most its memory bandwidth times that intensity, and can compute at most its peak
rate, so attainable performance is the lower of the two.

<RooflineChart />

The array add does one floating-point addition per 12 bytes moved, far left of
the ridge: memory bandwidth bounds it, so even perfect
[SIMD](/learn/computer-architecture-execution/simd-and-data-parallelism/) code
cannot pass the memory roof. A matrix multiply that reuses each value many times
sits far to the right, where faster arithmetic does help. The machine in the
figure is illustrative. To draw a real roofline, measure the machine's peak
bandwidth and compute rate, and count the bytes a kernel actually moves, which
caches can make lower than the source suggests.

## Counters test a cause

Hardware **performance counters** count events inside the processor while a
program runs: cycles, retired instructions, branches and branch misses, cache
references and misses. On Linux, `perf stat` runs a command and reports such
counts, `-e` chooses the events and `-r` repeats the command and reports the
spread. Ratios connect the counts to the CPU-time equation: instructions per
cycle (IPC) is the reciprocal of CPI. With illustrative numbers, not a recorded
run, 4.0 billion instructions in 2.5 billion cycles give an IPC of 1.6.

Counters need care:

- **Names are generic, events are not.** `cache-misses` maps to a
  model-specific event; check what it counts on your processor with `perf list`
  and the vendor's documentation before comparing machines.
- **Multiplexing.** A core has only a few counters. Ask for more events than
  that and the tool time-shares them and scales the counts up, reporting how
  much of the run each event was counted.
- **Hybrid processors.** Performance and efficiency cores have separate
  counters, so `perf stat` reports their counts separately unless told to merge
  them. Pinning the run to one core keeps a single type.
- **Scope and permission.** Counts cover the whole command, including start-up.
  The kernel's `perf_event_paranoid` setting and the `CAP_PERFMON` capability
  decide what an unprivileged user may count.

## Two-minute recap

- Treat a benchmark as an experiment: predict, fix the workload and
  environment, check results, repeat and alternate.
- Report a distribution: the median for a typical run and p10–p90 for spread;
  overlapping ranges mean you need more runs.
- Cache state, pinning and frequency are part of what you measure; record them.
- A roofline bounds a kernel by peak compute or by bandwidth × intensity;
  left of the ridge, move fewer bytes before computing faster.
- Counters test causes: IPC and miss counts, read with their definitions,
  multiplexing, hybrid cores and scope in mind.
