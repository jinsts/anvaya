  - prompt: What must caller and callee agree on for a function call to work?
    answer: >-
      Their calling convention specifies how arguments and results are passed,
      which registers each side must preserve, and how stack alignment is
      maintained. The call must also retain a return location so execution can
      resume after the call. Some architectures place it on the stack, while
      others use a link register that may later be saved. Compilers can omit or
      reshape frames when observable behavior and the interface rules permit it.
  - prompt: Does returning from a function destroy everything it created?
    answer: >-
      Returning ends the call's activation, but an independently allocated object
      can outlive that call. A local pointer or reference and its target have
      separate lifetimes. In a manual-allocation model, the target remains until
      explicitly released by its owner; in a tracing collector it can remain
      while reachable. Returning a reference to expired automatic storage is
      unsafe, unlike returning a reference to a still-live allocation.
  - prompt: Why can recursive code overflow the stack even when the machine has free RAM?
    answer: >-
      A thread normally has a finite stack budget, independent of the machine's
      total available RAM. Without an applicable optimization, every outstanding
      recursive call retains a frame, so depth multiplies per-frame demand.
      Replacing recursion with an explicit work structure can move that storage
      into independently managed memory but does not remove its size cost.
      Bound the depth or change the traversal according to the input constraints.
  - prompt: Does garbage collection eliminate memory leaks and lifetime reasoning?
    answer: >-
      A tracing collector can reclaim objects that are no longer reachable from
      its roots, including unreachable cycles. It cannot know that a reachable
      cache entry or listener is no longer useful to the application. Such
      retained references can keep memory growing, and reclamation timing is
      generally not a prompt resource-release guarantee. Files, locks and other
      resources still need appropriate explicit lifecycle handling.

      There is no universal comparison independent of allocator, size and context.
      Conventional stack reservation often adjusts a pointer, while a heap

      fresh pages. Initialization, page faults, synchronization and later
      reclamation can dominate either path. Choose from ownership and lifetime
      requirements, then measure the relevant workload.

## A returning function can leave a live result

Imagine a function that creates a large buffer and returns a reference to it.
The function's call ends, yet the caller still needs the buffer. If all storage
followed the lifetime of the call, that result would disappear too soon.

A stack of trays gives a useful picture of nested calls: remove the top tray
before reaching the one below. Heap allocations are more like separately checked
out tools that can be returned in a different order. These analogies explain
lifetime order, but they do not specify physical addresses, allocation algorithms
or a programming language's object placement.

The [compilation lesson](/learn/computer-architecture-execution/compilation-and-execution/)
explains how code reaches execution. The
[representation lesson](/learn/computer-architecture-execution/binary-and-data-representation/)
explains byte layout. Here we ask how long the storage holding those bytes stays
valid.

## Call frames preserve an unfinished computation

A **call frame**, also called an activation record, holds state associated with
one active function invocation. Depending on the target and compiler, that state
can include a return location, saved registers, arguments that do not fit in
argument registers, spilled values and space for local storage.

A conventional thread's **call stack** manages these frames in last-in,
first-out order. Suppose `main` calls `parse`, which calls `readField`. The calls
remain unfinished in that order, while `readField` executes. Returning from
`readField` resumes `parse`; returning from `parse` resumes `main`.

The **stack pointer** tracks the current stack boundary. A frame pointer, when
used, provides a stable base for references inside a frame. A compiler may omit
the frame pointer or keep a value entirely in a register. Source-level local
variables do not imply one fixed stack slot each.

A **calling convention** is the agreement that lets separately compiled functions
cooperate. It specifies argument and return-value locations, register-preservation
responsibilities and stack-alignment requirements. Caller-saved registers can be
clobbered by a call; the caller preserves any values it still needs. A callee
that uses a callee-saved register must restore the agreed value before returning.

On a conventional x86-64 call, the return address is pushed to the stack. Other
architectures may first place it in a link register. A nested callee then needs
to preserve that return information if the next call would overwrite it. Neither
mechanism makes the return address a pointer to a local variable: it identifies
where instruction execution resumes.

## Independently allocated storage has another lifetime

**Heap allocation** requests storage whose release need not follow the nesting
of calls. The term here refers to dynamically managed storage, not the heap data
structure used in a priority queue. A heap can span multiple mapped regions;
there is no requirement that all live allocations occupy one contiguous physical
area.

The temporary reference in the callee and the buffer it names have separate
lifetimes. Returning or copying a reference does not copy the whole target.
The API must say who may use the target, who releases it and when that release
is allowed.

In C, returning a pointer to an automatic local object whose lifetime ends on
return produces an invalid access if the caller later dereferences it. Returning
a pointer to a still-live allocation is a different operation. Its owner must
still avoid freeing it while another user needs it.

## Failure modes follow ownership and limits

A **dangling reference** names an object after its lifetime ends. A
**use-after-free** uses storage after its explicit release, and a **double free**
tries to release the same allocation twice. The old bytes may remain temporarily,
which can make a bug appear to work before reuse exposes it. Their persistence
does not extend the object's valid lifetime.

A **memory leak** retains storage the application no longer needs. With manual
allocation, losing the only owning pointer can make release impossible. With
automatic collection, keeping an obsolete object reachable from a long-lived
cache or listener can prevent reclamation.

**Stack overflow** means the thread's stack demand exceeds its allowed capacity.
Deep recursion and large frames can trigger it even while other memory remains
available. Conventional recursion with depth d and bounded frame size f needs
O(d × f) frame storage. An optimization such as tail-call elimination changes
that result only when the actual compiler and call permit it; do not assume it
for every language or function.

Rewriting recursion with an explicit array or linked work structure changes how
the pending work is represented. It can avoid a small call-stack budget, but
still needs space for the same unresolved work. Choose traversal order, input
limits and ownership deliberately.

## Allocation costs include more than reserving bytes

Conventional stack reservation often adjusts a pointer, with release following
return order. Initialization of a large local array still costs time proportional
to the initialized bytes, and obtaining previously untouched pages can add work.
The cheap pointer update is only one part of the operation.

A general allocator manages free regions, size classes and metadata. Small
requests may use an efficient local path; other requests can need coalescing,
synchronization or operating-system page allocation. One application allocation
does not necessarily require one system call.

**Internal fragmentation** is unused space inside an allocated block, such as
rounding a request to a larger size class. **External fragmentation** is free
space split into separated regions that cannot satisfy a larger contiguous
request under a nonmoving allocator's rules. A moving collector may compact
objects, provided it can update the necessary references. These policies trade
space, bookkeeping and pause behavior differently.

## Managed languages still need lifetime reasoning

A tracing garbage collector begins from **roots**, such as live execution state
and other runtime-defined reachable locations, and follows object references.
An object unreachable from every root can become eligible for reclamation.
Unreachable cycles do not need to remain forever under this model, unlike a
simple reference-counting system without cycle handling.

Eligibility is not a promise of immediate collection. A live reference held by
an old event listener or an unbounded cache can keep an otherwise unused object
reachable. Also, reclaiming memory does not by itself promptly close an open file
or release an application lock.

JavaScript specifies behavior and reachability-visible effects, not a universal
physical rule that every primitive is on the stack and every object is on the
heap. Runtimes can inline, eliminate or relocate storage when permitted. Keep
the language's lifetime contract separate from an illustrative memory diagram.

## Follow the shared native call

In the Linux x86-64 native example, the caller places the address of its unsigned
value in RDI. A `call` saves the address of the next instruction on the stack and
transfers control to `bump`; `ret` restores that continuation. The result arrives
in EAX. Caller-saved registers may change; preserved registers must be restored
if used. The checked `-O0` listing in the compilation lesson has an explicit
frame; the `-O2` leaf needs no local frame storage beyond the call's return address.
This is why a source function does not imply a fixed-sized physical frame.

**Unfamiliar trace:** a caller retains handle H to an allocation; the callee's
frame disappears; a later access through H succeeds; then H is released. Which
event invalidates another alias of H?

<details>
<summary>Check after answering</summary>

The release. It ends the allocation's lifetime for every alias; the earlier
return removed only the callee's frame and its local copy of the handle.
Copying or moving a handle cannot copy or extend its target.

</details>

## Two-minute recap

- A call frame preserves one unfinished invocation; nested calls normally return
  in last-in, first-out order.
- Calling conventions specify arguments, results, preserved state and alignment.
- A reference and its target can have different lifetimes.
- Heap allocation permits independent lifetimes but still needs an ownership and
  reclamation policy.
- Stack overflow, dangling references and retained allocations are different
  failure mechanisms.
- Garbage collection handles reachability; physical placement and prompt resource
  release require separate reasoning.
