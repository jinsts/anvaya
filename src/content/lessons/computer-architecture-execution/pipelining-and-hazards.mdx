interviewQuestions:
  - prompt: Does pipelining make an individual instruction faster?
    answer: >-
      No. Each instruction still passes through every stage, and pipeline
      registers between stages can make its latency slightly longer.
      Pipelining raises throughput: with five stages, up to five instructions
      are in progress at once, so in the ideal case one finishes every cycle.
      Shorter stages also allow a faster clock. Hazards are what keep real code
      from reaching one instruction per cycle.
  - prompt: What is a pipeline hazard, and what kinds are there?
    answer: >-
      A hazard is a situation in which the next instruction cannot proceed in
      the next cycle. A data hazard is a dependence on a result that is not
      ready yet. A control hazard arises because the next instruction to fetch
      depends on a branch that has not been resolved. A structural hazard is
      two instructions needing the same hardware in the same cycle. The
      pipeline stalls, inserting bubbles, or flushes wrong-path instructions.
  - prompt: Why does a load followed by an instruction that uses its value still stall when forwarding exists?
    answer: >-
      Forwarding passes a result from the end of one instruction's EX stage to
      the start of the next one's EX. A load's value arrives only at the end of
      MEM, one stage later, so the dependent instruction must wait one cycle
      even with forwarding: the load-use bubble. A compiler hides it by placing
      an independent instruction between the load and its use.
    followUps:
      - Why might a compiler still emit the dependent instruction right after the load?
  - prompt: What does a taken branch cost in a simple pipeline, and how do processors reduce that cost?
    answer: >-
      If the pipeline fetches the next sequential instructions and the branch
      is resolved in EX, a taken branch discards the two instructions fetched
      behind it, a two-cycle penalty. Resolving branches earlier shortens it,
      and branch prediction avoids it whenever the prediction is right. Deep
      modern pipelines resolve branches many stages after fetch, so a
      misprediction costs far more and accurate prediction matters more.

## One instruction per cycle, almost

The [execution lesson](/learn/computer-architecture-execution/how-computers-execute-programs/)
ran one instruction through the whole datapath before starting the next. Most of
the datapath sat idle most of the time. A **pipeline** splits execution into
stages and starts a new instruction every cycle, so several are in progress at
once.

A laundry with a washer, a dryer and a folding table works the same way: while
one load dries, the next washes. Each load takes as long as before, but loads
finish more often. The analogy stops at dependences. A load of laundry never
needs the previous load's result; instructions often do.

## Five stages, overlapped

The teaching pipeline has five stages: **IF** fetches the instruction, **ID**
decodes it and reads registers, **EX** computes in the ALU, **MEM** accesses data
memory and **WB** writes the result back to a register. Ideally a new instruction
enters IF every cycle, so after the pipeline fills one instruction finishes per
cycle: four instructions take 4 + 4 = 8 cycles instead of 4 × 5 = 20.

Pipelining improves **throughput**, instructions finished per unit of time, and
lets each stage, and so the clock cycle, be short. It does not shorten the
**latency** of a single instruction, which still passes every stage.

## Data hazards insert bubbles

A **data hazard** occurs when an instruction needs a register that an earlier
instruction has not produced yet. The pipeline must hold the dependent
instruction, leaving a **bubble**, an idle stage, behind it. **Forwarding**, also
called bypassing, removes most of these waits by routing a result from the end
of EX straight to the next instruction's EX, without waiting for write-back.

<PipelineTable />

Forwarding cannot help a load fully: its value is ready only at the end of MEM,
one stage after EX, so a dependent instruction right behind it waits one cycle.
This is the **load-use** bubble. The tables are computed by the lesson's tested
model, whose assumptions are stated in its source below.

## Control hazards flush wrong-path work

The next instruction to fetch depends on every branch before it. This pipeline
keeps fetching sequentially, in effect predicting "not taken", and learns the
branch's outcome in EX. If the branch is taken, the two instructions fetched
behind it are on the wrong path and are **flushed**: they never write a result,
and fetch restarts at the target. Each taken branch costs two cycles here; in
modern processors that resolve branches many stages after fetch, the cost of a
wrong guess is far higher, which is why the next lesson's branch predictors
matter.

A **structural hazard** is two instructions needing one piece of hardware in the
same cycle, such as a single memory for instruction fetch and data access. This
pipeline avoids it by design, with separate instruction and data memories and a
register file that writes in the first half of a cycle and reads in the second.

## Two-minute recap

- A pipeline overlaps stages of different instructions: higher throughput, not
  lower latency per instruction.
- Data hazards make a consumer wait for its producer; forwarding removes most
  waits, except the one-cycle load-use bubble.
- Reordering independent instructions fills bubbles without changing results.
- A taken branch resolved in EX flushes the instructions fetched behind it.
- Bubbles and flushes are why real code runs at more than one cycle per
  instruction.
