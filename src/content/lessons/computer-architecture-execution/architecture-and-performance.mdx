## The same Big-O can hide different work

Two programs both scan a million records, so both take O(n) time under a fixed
cost per record. One follows scattered pointers; another reads a compact array
containing only the fields it needs. Their asymptotic bounds can agree while
their instruction counts, cache traffic, and completion times differ.

Think of a kitchen assembly line. Overlapping chopping, cooking, and serving
can raise the number of meals finished per hour, but a dish still needs its
dependencies completed in order. The analogy stops at a processor's speculative
work and its ability to discard results before they become architectural state.

Use complexity analysis to explain how work scales. Use an architectural cost
model to form a hypothesis about a constant factor or bottleneck. Use
measurement to discover whether the hypothesis explains the actual workload.

## Count instructions, cycles, and seconds

For a fixed run, a useful CPU-time relation is:

**CPU time = executed instructions × average cycles per instruction / clock frequency.**

Cycles per instruction is abbreviated **CPI**. Its reciprocal, instructions per
cycle or **IPC**, is another aggregate measure over the same counted interval.
A superscalar core can complete multiple instructions per cycle on average, so
CPI may be below one. CPI is not a constant shared by every instruction or every
run of a processor.

The frequency form assumes a suitable fixed or effective frequency for the
interval. Frequency scaling, throttling, and the definitions of measured cycles
complicate using a nominal GHz number with counter readings. CPU execution time
also differs from elapsed time: waiting for I/O or being descheduled can make
wall-clock completion much longer.

Suppose a hypothetical run executes two billion instructions at CPI 1.5 and
3 GHz. The estimate is one second. A candidate executes 1.5 billion instructions
at CPI 1.8 and the same frequency: its estimate is 0.9 seconds. CPI gets worse,
yet total estimated time improves because the instruction reduction is larger.

## Overlap helps until dependencies or resources intervene

A **pipeline** divides work into stages and overlaps different instructions at
different stages. It primarily improves throughput and can enable a shorter
clock period; it does not promise that one instruction finishes sooner.

Three kinds of hazards limit overlap:

- A **data hazard** occurs when an instruction needs a result that is not ready.
- A **structural hazard** occurs when operations compete for a limited resource.
- A **control hazard** occurs when the next useful instruction depends on unresolved control flow.

Forwarding and scheduling can resolve some dependencies without waiting for
every earlier instruction to finish, but a dependent chain still has a critical
path. Multiple execution units cannot compute a sum before its required inputs
exist.

**Superscalar execution** uses multiple issue or execution opportunities per
cycle. **Out-of-order execution** finds ready independent work beyond a stalled
instruction while preserving the required architectural behavior. A common
implementation commits completed instructions in program order, even when their
execution overlapped or occurred in another order.

**Branch prediction** chooses a likely control-flow path before the branch is
resolved. **Speculation** executes work on that assumption. A wrong prediction
discards the affected speculative architectural results and redirects execution;
it can waste work and leave observable microarchitectural effects such as cache
changes. It does not give software permission to depend on an incorrect path's
architectural results.

## Make useful bytes easy to reach

The [memory hierarchy lesson](/learn/computer-architecture-execution/memory-hierarchy-and-caches/)
explained spatial and temporal locality. A contiguous scan can use more bytes
from each fetched cache line than pointer chasing. But “array” at the source
level does not establish the actual layout: runtime representation, element
types, and indirection still matter.

For a loop that reads only the temperature from each record, separate contiguous
temperature storage may fetch fewer unused bytes than records containing many
other fields. The alternative can be worse when every operation needs all
fields together. Compare the repeated accesses rather than declaring one layout
universally superior.

**SIMD**, single instruction multiple data, applies one operation to several data
lanes. Regular contiguous data and independent iterations can help a compiler
vectorize a loop. Aliasing, dependencies, control flow, alignment requirements,
and numeric semantics can limit that transformation. Vector width alone does
not establish speedup when memory bandwidth is already saturated.

On multicore systems, two threads can update distinct counters that occupy one
cache line. Coherence then coordinates writes to the shared line even though the
logical variables are independent. This is **false sharing**. Local accumulation
followed by a merge can reduce traffic. Padding may help if it actually separates
the counters for the target layout, but consumes space and can harm locality.

## Bound an optimization with Amdahl's law

Let `f` be the fraction of **baseline elapsed time** that remains unchanged, and
let `s` be the speedup applied to the remaining fraction. For the same workload
and no new overhead:

**Overall speedup = 1 / (f + (1 − f) / s).**

With `f = 0.25` and `s = 4`, normalized time is 0.4375 and speedup is about 2.286.
Even an arbitrarily fast improved portion cannot remove the remaining quarter;
the limiting speedup is four. The fraction describes baseline time, not a
percentage of source lines or functions.

When `s` represents ideal parallelization on four cores, the model assumes that
portion scales fourfold and adds no overhead. Real synchronization, load
imbalance, cache effects, and communication can change the result. Scaling the
input size with the core count asks a different question from this fixed-work
comparison.

## Turn a performance claim into an experiment

Before optimizing, state a falsifiable prediction: “This layout reduces memory
traffic for a scan that reads only temperatures.” Then define what a correct
result is and which evidence would support or weaken that explanation.

1. **Fix the workload.** Record inputs, output requirements, sizes, and the timed boundary. Separate startup from steady state when that distinction matters.
2. **Fix the environment.** Record machine, runtime or compiler, optimization options, thread count, and relevant background load.
3. **Validate results.** Check outputs outside the timed region where possible, while ensuring the optimizer cannot eliminate the work being studied.
4. **Repeat and alternate.** Collect a distribution and compare candidates under comparable cache and warmup policies. Avoid treating one short run as a stable result.
5. **Inspect causes.** Use available profiler samples, counters, and generated code to test the proposed mechanism. State counter definitions and measurement limitations.

An input sorted by a branch condition might improve prediction, change cache
behavior, or let optimization change the generated loop. A faster timing alone
does not distinguish those explanations. Likewise, fewer cache misses can
coexist with a slower program if extra instructions or synchronization outweigh
the benefit. Report the observed outcome separately from the causal inference.

## Two-minute recap

- CPU time depends on instruction count, average CPI, and cycle duration together.
- Pipelines and multiple execution units exploit overlap; dependencies and hazards limit it.
- Locality, SIMD, and false sharing depend on actual accesses and data layout.
- Amdahl's law bounds a fixed-work improvement using baseline time fractions.
- Elapsed time, CPU time, throughput, and hardware counters describe different things.
- Verify correctness, measure repeatably, and test the proposed cause separately from the timing result.
