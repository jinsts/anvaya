  - prompt: Why can two executions with the same instruction count take different amounts of time?
    answer: >-
      An instruction count measures completed work at the instruction-set level,
      not how long operands take to arrive. Cache misses, dependencies and branch
      prediction change the cycles required, while frequency and scheduling
      affect elapsed time. Pipelining also overlaps work on several instructions.
      A useful comparison therefore states the processor, workload and measured

      while respecting dependencies and the architecture's ordering rules.
      Speculative work must be prevented from committing an incorrect
      architectural result. The internal execution order therefore need not be
      the same as the order used to explain the program's committed state.

## A program is a sequence of state changes

Suppose a counter begins at two and is reduced until it reaches zero. A source
language might hide the steps behind a loop. At the machine level, each
instruction reads some state, performs an operation, and chooses what happens
next. Following those changes is the foundation of reading a crash report or
explaining a performance surprise.

Think of a musician following a score. The score is stored information; the
current position and the notes being played describe an execution. A repeat mark
changes which part comes next. The analogy stops at meaning: a processor follows
encoded operations and state transitions, without understanding the program's
purpose.

A **stored-program computer** keeps instructions in memory as well as data. The
processor contains control circuitry, arithmetic and logic circuitry, and small
storage locations called **registers**. Memory holds the larger working set;
input and output connect execution to devices. Modern systems refine this model
with caches and separate instruction and data paths, but it remains a useful
starting point.

## Trace a deliberately small machine

Our illustrative machine has one eight-bit **accumulator**, a register that
holds the arithmetic result. Its unsigned values range from 0 through 255;
addition wraps modulo 256. Its PC counts instruction positions, beginning at
zero. That choice makes the trace small; it is not an x86-64 or ARM64 encoding.

The program sets the accumulator to 2, adds 255, branches back to the add while
the result is nonzero, then halts. Adding 255 modulo 256 has the effect of
subtracting one. Before each instruction, predict both the new accumulator and
where the PC will point afterward.

| Instruction position | Operation in this teaching machine    | Next effect                |
| -------------------- | ------------------------------------- | -------------------------- |
| 0                    | Set accumulator to 2                  | Continue at 1              |
| 1                    | Add 255 modulo 256                    | Continue at 2              |
| 2                    | Branch to 1 if accumulator is nonzero | Otherwise continue at 3    |
| 3                    | Halt                                  | Stop with PC retained at 3 |

After the first addition the accumulator is 1, so the branch returns to instruction
position one. After the second it is 0, so the branch continues to position 3.
The branch executes twice, even though it appears once in the program.
**Static instruction count** counts instructions in the program; **dynamic
instruction count** counts the instructions actually executed.

Each output line shows PC and accumulator after a state transition, with the

the full sequence, unsigned wraparound, taken and untaken branches, invalid
operands, and the step limit.

The model invariant is that every successful step uses a valid instruction
position and keeps the accumulator within one unsigned byte. Invalid control
flow throws instead of reading arbitrary host memory. A step budget stops an
endless loop; reaching the budget is a simulator limit, not evidence that a real
program would eventually halt.

## Separate program behavior from processor timing

The trace completes six instructions: one set, two additions, two branches and
one halt. It contains no clock model. Six instructions do not imply six cycles,
six nanoseconds, or any particular hardware speed.

A pipeline overlaps instruction stages. The [performance lesson](/learn/computer-architecture-execution/architecture-and-performance/) works the latency, throughput and dependency timeline.

Our TypeScript implementation validates p stored instructions and records s
executed steps. Under constant-cost operations on these bounded values, its
work is O(p + s) and its retained trace uses O(s) space. Those are simulator
costs. A production emulator could keep only its current state when no history
is needed; this teaching version keeps history so you can inspect it.

## The operating system supplies an execution context

A file containing instructions is a **program**. A **process** gives a running
instance an address space, saved execution state and resources. The operating
system arranges initial execution and schedules threads onto processors. A
single-threaded process may stop running while another uses the same core, then
resume from saved state.

Our model omits loading, address translation, interrupts and multiple threads.
It also uses a halt instruction to finish the demonstration; an ordinary hosted
application normally exits through its runtime and operating system. Keep the
layers separate when diagnosing a failure: the PC explains control flow, while
the process and runtime explain which memory and services that flow can use.

## Two-minute recap

- A program defines operations; execution changes registers, memory and control flow.
- The PC selects the next instruction; a branch can replace the normal successor.
- Static instructions and dynamically executed instructions are different counts.
- A sequential trace describes committed behavior without predicting hardware timing.
- Pipelining can improve throughput while each instruction still has several stages.
- A process supplies an execution context; this simulator models only a small part of it.
