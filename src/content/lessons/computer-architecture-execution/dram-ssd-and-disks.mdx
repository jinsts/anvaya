    answer: >-
      Orders of magnitude, not exact figures: a cache hit takes about a
      nanosecond or a few, a DRAM access around 100 nanoseconds, an SSD read
      on the order of 100 microseconds, and a random hard disk read several
      milliseconds. Each step is roughly a hundred to a thousand times the one
      before. They depend on the hardware and on whether requests overlap, so
      measure the target before relying on a number, but the ratios are what
      design decisions such as caching and batching rest on.

      Make each load depend on the previous one, for example by chasing
      pointers through a random cycle of nodes, one per cache line. The
      processor cannot start the next load before the current one returns, and
      the prefetcher cannot guess the next address, so time per load
      approaches the latency of the level that holds the working set. Sweep the
      working-set size, repeat and interleave runs, and record the cache sizes

  - prompt: Why are small random reads so slow on a hard disk compared with sequential reads?
    answer: >-
      Each random read must move the arm to the right track and wait for the
      sector to rotate under the head, several milliseconds in total, before
      any data moves. For a 4 KiB read that positioning is almost the entire
      time, so the drive delivers well under 1 MB/s. A sequential read pays the
      positioning once and then streams at the transfer rate, often over
      100 MB/s.
  - prompt: Why can an SSD's write performance drop as it fills up?
    answer: >-
      Flash pages can be written only after their whole block is erased, so
      an overwrite goes to a new page and leaves the old one invalid. Garbage
      collection later copies a block's remaining valid pages elsewhere and
      erases it. The fuller the device, the more valid data each collected block
      holds, so each host write causes more internal copying: higher write
      amplification, lower throughput and more wear. Overprovisioning and TRIM
      give the device more free space to work with.
  - prompt: Why is reading DRAM sequentially faster than reading it randomly, even ignoring caches?
    answer: >-
      Reading DRAM opens an entire row into the sense amplifiers. Further
      reads from that open row only select columns, which is much cheaper
      than closing it and opening another row. Sequential addresses tend to
      fall in the same open row, and they also let caches use whole lines and
      prefetchers fetch ahead; random addresses defeat all three.

## Every miss has a price

A cache miss is not a fixed cost. It is answered by whichever level below holds
the data: another cache, DRAM, or, after a page fault, an SSD or a disk. Those
answers differ by factors of a thousand. Knowing the rough price of each level
lets you estimate before you measure: whether a design that touches DRAM a
million times is fast enough, or whether one random disk read per request is
already too many.

Think of fetching a book: from your desk, from the shelf, from the library
basement, from another city. Each trip is far longer than the one before, so
you plan which books stay close. The analogy stops at overlap: a processor can
have several requests in flight at once, and storage devices queue them, so
throughput can be much better than one trip at a time suggests.

## Each level is a different technology

<LatencyLadder />

Registers and caches are SRAM on the processor die. Main memory is DRAM, which
stores each bit as charge on a capacitor: about twenty times denser than SRAM,
and slower. SSDs store bits in flash cells, and hard disks in magnetic regions
on spinning platters. Capacity grows down the ladder and so does latency, by
roughly a hundred to a thousand times per step. Those ratios, more than any
single number, are what to remember.

## DRAM reads a whole row at a time

<DramRowBuffer />

A DRAM bank is a grid of cells. A read first **activates** a row, copying the
whole row into sense amplifiers, then reads the requested **column** from them.
While the row stays open, more reads from it need only the column step. Reading
another row first **precharges**, closing the open one. DRAM cells also leak,
so every row is refreshed periodically.

A memory system has several banks per chip and one or more channels, so a
controller can overlap work on different banks and channels. That is why
sequential access is fast twice over: it reuses open rows, and it lets caches
use whole lines and prefetchers run ahead. Random access pays the full
activate-and-read sequence and leaves bandwidth idle.

## Flash writes once, then erases a block

<FlashBlocks />

Flash is read and written in **pages** of a few kilobytes, but a page can be
written again only after its whole **erase block**, often 128 or 256 KiB, is
erased. Reads take tens of microseconds, writes hundreds, and erases
milliseconds, and each block survives a limited number of erase cycles.

An SSD hides this behind a **flash translation layer** that maps logical pages
to physical ones. An overwrite goes to a fresh page and marks the old one
invalid. **Garbage collection** copies a block's remaining valid pages and
erases it. Those internal copies are **write amplification**: more flash writes
than the host asked for, which costs throughput and wear. Spreading erases
evenly is **wear leveling**. A fuller drive leaves the collector less room, so
its blocks hold more valid pages to copy.

## A disk read waits for the arm and the platter

<DiskTime />

A hard disk read has three parts: **seek**, moving the arm to the track;
**rotation**, waiting for the sector to turn under the head, half a revolution
on average; and **transfer**, reading the data. For small random reads the
first two are nearly all of it. That is why databases and file systems work so
hard to read and write disks sequentially and in large pieces.

## Estimate before you measure

Use the ratios. Following a linked list of a million nodes scattered over
64 MiB is a million dependent DRAM accesses: on this machine's plateau, a
million times its "larger than L3" median, a fraction of a second. If each
node instead required a random read from a disk, a million reads at about
10 ms each would take hours. An SSD falls in between at minutes. The same
algorithm, in the same big-O class, spans six orders of magnitude depending on
where its data lives.

## Two-minute recap

- Cache, DRAM, SSD, disk and network latencies differ by roughly a hundred to a
  thousand times per step; remember the ratios.
- Dependent pointer chasing over a random cycle measures latency; the sweep's
  steps line up with the recorded cache sizes, and the last one starts early.
- DRAM opens a whole row; row hits are cheaper than closing and opening rows.
- Flash pages are written once per block erase; garbage collection causes write
  amplification.
- Disk time is seek + rotation + transfer; small random reads are almost all
  positioning.
