## A crash report is a list of frames

A program crashes deep inside a parser, and the debugger prints a backtrace:
`readField`, called from `parse`, called from `main`. Nothing in the source
lists those three calls together. The debugger found them on the stack, where
each unfinished call left the address to return to. The same stack can run out
when a recursion goes too deep, even on a machine with gigabytes of free memory.

Think of reading with bookmarks: you follow a footnote into an appendix, and
from there a reference into another chapter, leaving a bookmark at each place
you left. You come back through them newest first. The analogy stops at
contents: a frame holds more than a place to resume, such as saved registers,
arguments and locals, and the compiler decides how big it is, or whether it
exists at all.

The [assembly lesson](/learn/computer-architecture-execution/reading-assembly/)
stepped `scale_sum` calling `sum_to`. This page follows what that call does to
the stack.

## Frames keep unfinished calls

A **call frame**, also called an activation record, holds state associated with
one active function invocation. Depending on the target and compiler, that state
can include a return location, saved registers, arguments that do not fit in
argument registers, spilled values and space for local storage.

A conventional thread's **call stack** manages these frames in last-in,
first-out order. Suppose `main` calls `parse`, which calls `readField`. The calls
remain unfinished in that order while `readField` executes. Returning from
`readField` resumes `parse`; returning from `parse` resumes `main`.

The stack grows toward lower addresses. The **stack pointer**, rsp, marks its
top, and a **frame pointer**, rbp, when the compiler keeps one, gives a fixed
base for addressing a frame's slots. Here is what GCC's unoptimized code
actually keeps on the stack while `scale_sum` waits for `sum_to`:

<RealFrames />

Each frame holds the return address its caller's `call` pushed, the caller's
saved frame pointer, and slots for the function's arguments and locals. At
`-O2` the same functions keep everything in registers, and `sum_to` needs no
frame at all: a source function does not imply a fixed physical frame. On ARM64
the return address arrives in the link register instead, and a function that
calls another saves it in its frame.

## Follow the stack pointer

Six kinds of instruction move rsp. `call` pushes the 8-byte return address and
jumps; `ret` pops it back into the instruction pointer. `pushq` and `popq` move
8 bytes. `subq $N, %rsp` reserves N bytes for locals and `addq` releases them.
`movq %rsp, %rbp` starts a frame pointer, and `leave` undoes it: it copies rbp
back into rsp, then pops the caller's saved rbp. Measure everything as the
**depth**: bytes below rsp's value when the function was entered.

The System V x86-64 calling convention adds two rules. The callee must preserve
rbx, rbp and r12–r15 for its caller, which is why `scale_sum` at `-O2` pushes rbx
before using it. And rsp must be a multiple of 16 immediately before every
`call`. When the function was entered, its caller's call had just pushed 8
bytes onto an aligned stack, so rsp was 8 bytes past a multiple of 16. A call at
depth d is therefore aligned when d − 8 is a multiple of 16.

Predict before opening the trace: before its call, `scale_sum` at `-O0` runs
`pushq %rbp`, `movq %rsp, %rbp` and `subq $16, %rsp`, and at `-O2` only
`pushq %rbx`. What is the depth at each call, and is each call aligned?

At `-O0` the push leaves depth 8 and the subtraction 24, and 24 − 8 = 16 is a
multiple of 16, so the call is aligned. The 16 reserved bytes hold copies of
the three arguments: values at −8(%rbp), count at −12 and factor at −16. `leave`
returns to depth 0 in one instruction. At `-O2` one push leaves depth 8, and
8 − 8 = 0: aligned with nothing reserved, because pushing rbx also did the
padding.

</details>

A function that calls nothing, a **leaf**, needs no alignment and may not move
rsp at all. The convention reserves the 128 bytes below rsp, the **red zone**,
which signal and interrupt handlers must not touch, so a leaf may keep its
whole frame there. In the frame figure above, `sum_to` at `-O0` sets its frame
pointer and stores its locals below rsp without a `subq`.

## Depth costs stack space

**Stack overflow** means the thread's stack demand exceeds its allowed capacity.
Deep recursion and large frames can trigger it even while other memory remains
available. Conventional recursion with depth d and bounded frame size f needs
d × f bytes of frames: a 1 MiB stack holds 16,384 frames of 64 bytes. An
optimization such as tail-call elimination changes that result only when the
actual compiler and call permit it; do not assume it for every language or
function.

Rewriting recursion with an explicit array or linked work structure changes how
the pending work is represented. It can avoid a small call-stack budget, but
still needs space for the same unresolved work. Choose traversal order, input
limits and ownership deliberately.

## Two-minute recap

- A call frame holds one unfinished call: its return address, saved registers,
  arguments and locals. Frames return newest first.
- `call` pushes the return address and `ret` pops it; rsp marks the top of the
  stack, and rbp, when kept, a fixed base.
- System V x86-64 needs rsp 16-byte aligned at each call. Entry is 8 bytes off,
  so a function pads when its pushes leave the call misaligned.
- A leaf may keep its frame in the 128-byte red zone below rsp.
- Recursion needs depth × frame size bytes of stack, however much RAM is free.
