  - prompt: Why is UTF-8 the usual encoding for files and network protocols?
    answer: >-
      ASCII text is unchanged in UTF-8, so older tools and protocols keep
      working. The encoding has no byte-order variants, because it is a
      sequence of single bytes. Lead and continuation bytes have distinct bit
      patterns, so a reader can find the start of a character from any position,
      and a corrupted byte damages only one character. Text dominated by

  - prompt: What is endianness, and when does it matter in application code?
    answer: >-
      It is the order in which a multi-byte value's bytes are stored at
      increasing addresses: little-endian puts the least significant byte first,
      big-endian the most significant. Arithmetic in registers is unaffected. It
      matters when bytes cross a boundary, such as a file format, a network
      protocol or a memory-mapped buffer read by another machine. Formats should
      name their order, and code should convert explicitly, for example with
      `DataView`'s endianness argument.

      The ABI requires each field to start at an address that is a multiple of
      its alignment, so the compiler inserts padding before a field when needed.
      The struct's size is also rounded up to its largest alignment, so every
      element of an array stays aligned. Ordering fields from largest to
      smallest alignment usually removes most padding, but reordering changes a
      binary interface, so it is a design decision for public types.

## Three bugs from the same cause

A form accepts a 20-character name, and the database rejects it for exceeding
20 bytes. A client reads a 32-bit length from a file and gets 2,018,915,346
instead of 305,419,896. A service sends a C struct over a socket, and the
receiver reads garbage from its third field. Each value was correct. Each
reader assumed the wrong rule for how a value occupies **several bytes**.

The [representation lesson](/learn/computer-architecture-execution/binary-and-data-representation/)
gave a single byte its meaning. This page covers values that need more than
one: text, whose characters need one to four bytes each; integers, whose bytes
can be stored in either order; and records, whose fields need aligned
addresses. Think of a moving truck: the same furniture fits differently
depending on the packing rules, and the person unloading must know them. The
analogy stops at flexibility: a byte layout is a contract, and a reader that
guesses gets wrong values rather than an untidy truck.

## UTF-8 spends one to four bytes per code point

Unicode gives every character a **code point**, a number written U+0041 for
"A". An encoding turns code points into stored units. **UTF-8** uses bytes and
picks a template by the code point's range:

<Utf8Encoding />

The lead byte's high bits say how many bytes follow, and every continuation
byte starts with `10`. Because the patterns differ, a reader dropped into the
middle of UTF-8 text can find the next character boundary, and ASCII text, all
below U+0080, is unchanged. Code points U+D800 to U+DFFF are never encoded:
they are reserved for UTF-16.

**UTF-16** uses 16-bit code units. Code points up to U+FFFF take one unit;
larger ones are split across a **surrogate pair**, a high unit from D800–DBFF
and a low unit from DC00–DFFF. JavaScript strings are sequences of UTF-16 units.

## Count in the unit the task needs

<TextLadder />

A **grapheme** is what a reader sees as one character. Unicode defines its
boundaries, and one grapheme can hold several code points, such as a letter
followed by a combining accent, or the two regional-indicator code points of a
flag. The four counts answer different questions:

| Question                                          | Count        | JavaScript                                      |
| ------------------------------------------------- | ------------ | ----------------------------------------------- |
| Will it fit in a byte-limited column or packet?   | UTF-8 bytes  | `new TextEncoder().encode(s).length`            |
| What does `s.length` or `s[i]` mean?              | UTF-16 units | `s.length`                                      |
| How many Unicode characters were encoded?         | Code points  | `[...s].length`                                 |
| How far should the cursor move or truncation cut? | Graphemes    | `Intl.Segmenter` with `granularity: 'grapheme'` |

Cutting text at the wrong unit corrupts it. Slicing a JavaScript string by
units can split a surrogate pair; truncating UTF-8 bytes can cut a sequence in
half; truncating code points can strip an accent from its letter.

## Byte order decides which byte comes first

<ByteOrderLanes />

Memory is addressed in bytes, so a 32-bit value occupies four consecutive
addresses. **Little-endian** machines store the least significant byte at the
lowest address; **big-endian** machines store the most significant byte there.
Arithmetic in registers does not depend on it. It matters when bytes leave the
machine or are reinterpreted: the file in the opening read `12 34 56 78` as a
little-endian value and got 0x78563412, which is 2,018,915,346.

Formats therefore name their order. Internet protocols use big-endian
**network byte order**. In JavaScript, `DataView` methods take an explicit
`littleEndian` argument; never rely on the host's order for data that crosses a
boundary. Floating-point values follow the same rule: the recorded program
prints binary32 0.1, pattern `3dcccccd`, as `cd cc cc 3d`.

## Alignment adds padding between fields

Hardware reads an aligned value, one whose address is a multiple of its size,
in a single access. The x86-64 ABI therefore gives each type an **alignment**:
1 for `char`, 4 for `int32_t`, 8 for `double`. A compiler places each field at
the next offset that is a multiple of its alignment, inserting **padding**
bytes when needed, and rounds the record's size up to its largest alignment so
that every element of an array is aligned too.

Reordering is not always free. A struct that other code or files already depend
on has a fixed binary layout, and grouping fields by alignment can separate
fields that are used together. Packing attributes remove padding entirely, at
the cost of misaligned fields that the processor or compiler must access with
extra work. To send a record anywhere, encode each field explicitly in a
named byte order instead of copying its raw bytes, which include the padding.

## Two-minute recap

- UTF-8 encodes a code point in one to four bytes; lead bytes announce the
  length and continuation bytes start with `10`.
- UTF-16 uses one 16-bit unit up to U+FFFF and a surrogate pair above it;
  JavaScript's `length` counts these units.
- Bytes, UTF-16 units, code points and graphemes are four different counts:
  choose by the task.
- Little-endian stores the least significant byte first; formats that cross
  machines must name their byte order.
- Fields start at multiples of their alignment, and size rounds up to the
  largest alignment; ordering by alignment reduces padding.
