## A counter that stops counting

A service counts events in a 32-bit floating-point variable. For months the
count grows normally. At 16,777,216 it stops: every `count += 1` leaves it
unchanged, and no error is reported. In the same codebase, `0.1 + 0.2` prints
`0.30000000000000004`. Both surprises have one cause. A floating-point format
stores a fixed number of significant bits, and every result is rounded to fit.

Scientific notation is the right picture. Writing 6.02 × 10²³ keeps three
significant digits whatever the exponent, so the next value you can write,
6.03 × 10²³, is far away, while 6.02 × 10⁻³ has very close neighbors. The
analogy stops at the base: floating point uses powers of two, so a decimal
fraction such as 0.1 has no finite form and is rounded the moment it is stored.

The [representation lesson](/learn/computer-architecture-execution/binary-and-data-representation/)
gave integers their meaning. This page does the same for the IEEE 754 binary32
format, C's `float`. JavaScript numbers use binary64, C's `double`, which
follows the same rules with wider fields.

## Three fields, one formula

<Float32Anatomy />

A binary32 value has three fields. The **sign** bit gives the sign. The 8-bit
**exponent** field stores the power of two plus a **bias** of 127, so stored 123
means 2⁻⁴; the bias lets one unsigned field cover both large and small scales.
The 23-bit **fraction** gives the digits after the binary point. For normal
values the digit before the point is always 1, so it is not stored:

**value = (−1)^sign × (1 + fraction ÷ 2²³) × 2^(exponent − 127)**

The implicit 1 gives 24 bits of precision from 23 stored bits, about seven
significant decimal digits. In binary, one tenth repeats `0011` forever, so the
fraction keeps 23 bits and rounds the rest. The stored value is slightly more
than 0.1, as the figure's last line shows exactly. binary64 uses an 11-bit
exponent with bias 1023 and a 52-bit fraction: 53 bits of precision, about 16
decimal digits, and the same rounding.

## The exponent field also marks special values

The smallest and largest exponent fields do not follow the formula:

| Exponent field | Fraction 0                | Fraction not 0               |
| -------------- | ------------------------- | ---------------------------- |
| 0              | Zero, with a sign: ±0     | **Subnormal**: ± 0.f × 2⁻¹²⁶ |
| 1–254          | Normal: ± 1.f × 2^(e−127) | Normal: ± 1.f × 2^(e−127)    |
| 255            | ±Infinity                 | **NaN**, "not a number"      |

**Subnormal** values drop the implicit 1, so they fill the gap between zero and
the smallest normal value, 2⁻¹²⁶, in even steps of 2⁻¹⁴⁹. Results shrink toward
zero gradually instead of jumping to it. Infinity is the result of an overflow
or of dividing a nonzero value by zero. NaN marks an invalid result such as
0 ÷ 0 and is unequal to everything, itself included. The two zeros compare
equal, yet `1 / -0` is −Infinity.

## The gap doubles at every power of two

<FloatSpacing />

Between 2ᵏ and 2ᵏ⁺¹ the fraction offers 2²³ evenly spaced values, so the gap
between neighbors is 2ᵏ⁻²³. Moving up one power of two doubles the interval and
doubles the gap. The relative gap, the step divided by the value, stays near
2⁻²³ everywhere: the format keeps the same number of significant bits at every
scale, not the same number of decimal places.

That explains the counter. From 2²⁴ upward the gap is 2, so binary32 can no
longer store every integer. binary64 reaches the same point at 2⁵³, which is why
JavaScript's `Number.MAX_SAFE_INTEGER` is 2⁵³ − 1. It also explains why one
fixed tolerance cannot suit every comparison: 10⁻⁶ is far wider than the gap
near 1, and much narrower than the gap near 10¹⁰.

## Halfway values round to even

<RoundingTies />

A result that falls between two neighbors is rounded to the nearer one. The
default IEEE 754 rule breaks a tie by choosing the neighbor whose last fraction
bit is 0, called **round to nearest, ties to even**. Always rounding ties up
would push long computations upward on average; choosing the even neighbor
rounds ties down about as often as up. JavaScript's `Math.fround` performs this
rounding from binary64 to binary32, and the tests check both cases in the figure.

## Every addition rounds

<SummationOrder />

Rounding happens after every operation, not once at the end. When a large total
meets a small addend, the exact sum can fall between neighbors and round back to
the total: the addend disappears. Adding the small values first lets them build
up to something the large total can absorb.

So floating-point addition is not associative. In binary64,
`(0.1 + 0.2) + 0.3` gives `0.6000000000000001` while `0.1 + (0.2 + 0.3)` gives
`0.6`. Because reordering can change a result, C compilers keep the written
order of floating-point operations by default; GCC reassociates them only under
options such as `-fassociative-math`, which its manual notes can change results.
A parallel sum that combines partial results in a different order can likewise
return a slightly different total.

To reduce summation error:

- **Accumulate in a wider format**, for example sum binary32 data in binary64.
- **Sum pairwise or small-first** when magnitudes differ widely.
- **Use compensated summation.** Kahan's method carries each addition's rounding
  error into the next one; in the figure it recovers the exact 16,777,220.

## Choose a representation for the job

- **Exact quantities.** Money, counts and identifiers are exact by definition.
  Store money as integer minor units with a checked range, or use a decimal
  type with an explicit rounding rule.
- **Comparisons.** Compare within a tolerance derived from the calculation's
  magnitude and error, use an absolute tolerance near zero, and test NaN with
  `Number.isNaN`.
- **Width.** binary32 halves memory and bandwidth, which matters for large
  arrays, but keeps about seven digits and exact integers only up to 2²⁴.
  binary64 is the safer default for accumulation.
- **Display is not storage.** Printing fewer digits changes the text, not the
  stored value. Round when you produce output, and keep full precision in
  between.

## Two-minute recap

- binary32 stores sign, an exponent biased by 127, and 23 fraction bits after
  an implicit 1: 24 bits of precision.
- Exponent fields 0 and 255 encode zeros, subnormals, infinities and NaN.
- Each power-of-two interval holds the same number of values, so the gap
  doubles with the interval; integers stop being exact at 2²⁴ (2⁵³ in binary64).
- Halfway results round to the neighbor whose last bit is 0.
- Every operation rounds, so addition is not associative and summation order
  matters; wider accumulators, pairwise sums and Kahan summation reduce error.
- Store exact quantities as integers or decimals; compare floats with
  tolerances chosen for the problem.
